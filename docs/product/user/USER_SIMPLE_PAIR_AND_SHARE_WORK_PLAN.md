# 用户需求：两台设备简单配对与分享

状态：产品需求草案；安全设计需评审  
优先级：P1  
建议顺序：前四个单机闭环稳定后  
与 #30 关系：作为 Friend Mesh 的更小用户价值切片

## 1. 一句话目标

两个普通用户通过二维码或短邀请码安全配对，随后能立即发送一条消息、一个小文件
或一张内容卡片；第一版不同时承担完整社交网络、复杂服务 ACL 和跨公网承诺。

## 2. 为什么缩小 Friend Mesh 第一版

完整 Friend Mesh 计划同时包含邀请、关系凭证、撤销、深链、朋友权限、Private AI
friends-only 服务、跨网络可达和安全存储，范围大且存在设计门槛。用户真正感知的
第一个价值更简单：

> “我能不能把我的 Ryn 和另一个人的 Ryn 连起来，并马上分享一个东西？”

当前已经有签名 Peer 身份、发现、加密消息、小附件和内容发布/获取基础，但缺少
非技术用户可完成的配对入口。Peers 页依赖已经发现的节点，无法解释如何让一个
现实中的朋友出现在列表里。

本需求先关闭“相识 → 配对 → 第一次发送 → 撤销”的最短闭环，再把 Private AI
授权和更复杂服务放到后续版本。

## 3. v1 边界决策

第一版建议明确限制为以下之一，并在编码前由维护者批准：

- **同一局域网配对**；或
- **双方端点已可达的直接配对**。

如果没有经过验证的加密 Relay/P2P 邀请接受通道，不宣传“任何网络扫码即连”。
UI 必须在生成和接受邀请前显示当前可达范围。

v1 权限仅包括：

- 查看对方当前签名身份和已审核端点；
- 发送端到端加密文字消息；
- 发送有大小上限的小附件；
- 发送内容引用卡片，接收方自行决定是否获取内容。

不包括：

- 使用对方 Private AI；
- VPN/网络出口；
- 文件系统或 Agent 工具；
- 信任根资格；
- 自动发布或自动下载大文件；
- Credits 转账。

## 4. 核心用户旅程

### 4.1 发起配对

1. 用户点击“连接朋友”；
2. Ryn 显示当前网络范围、节点名称和可达性；
3. 用户选择短有效期；
4. 本机生成一次性邀请；
5. 本地渲染 QR，同时提供复制邀请码；
6. 用户可查看和取消未使用邀请。

邀请秘密离开创建页后不再次展示。二维码不得调用第三方生成服务。

### 4.2 接受配对

1. 对方扫描或粘贴邀请；
2. Ryn 仅在本地解析和验签；
3. Review 页面显示邀请者名称、身份指纹、网络、端点地址类型、有效期和权限；
4. 用户点击“连接”之后才联系邀请者；
5. 成功后双方显示“已连接”；
6. 自动进入第一次发送页面，但不自动发送内容。

### 4.3 第一次分享

配对成功页给出三个主操作：

- 发一条消息；
- 发一个小文件；
- 从“我的内容”选择一个条目发送内容卡片。

接收内容卡片时先展示元数据、来源、发布者、大小和安全状态；下载正文或文件需要
接收方确认，不能因为成为好友就自动获取任意内容。

### 4.4 断线与恢复

- 好友离线时，消息可以进入有界待发送队列或明确显示未送达；
- 不无限保存附件和重试；
- 重新发现同一签名身份后恢复连接；
- 端点变化需要验证，显著变化时要求再次确认；
- 用户看到的是“离线/重试中/需要确认”，而不是底层 Transport 错误。

### 4.5 撤销

1. 用户在好友详情点击“断开连接”；
2. 显示会失去的能力和未发送项目；
3. 本地立即撤销关系凭证并拒绝后续请求；
4. 向对方发送签名撤销通知，失败时有界重试；
5. 本地聊天历史由用户选择保留或删除；
6. 重新连接必须创建并接受新邀请，不能自动复活旧关系。

## 5. 邀请与关系安全

复用完整 Friend Mesh 方案中的核心原则：

- friendship 与 `trusted_roots` 完全分离；
- 不在链接中放 `RYNMESH_NETWORK_KEY` 或 local-control token；
- 邀请签名、短期、一次性、可取消；
- 邀请仅用于一次接受，成功后轮换成独立关系凭证；
- 关系请求绑定 peer ID、method、path、timestamp、nonce 和 body digest；
- 防重放、权限收窄、端点安全和速率限制在接收端执行；
- 无效邀请返回不泄漏服务存在性的通用失败；
- 日志、诊断和截图证据中不得出现原始邀请或关系秘密。

## 6. 数据模型

### 邀请记录

- invite ID/version；
- secret hash，不保存可重新展示的原始秘密；
- 创建、到期、使用、取消时间；
- 发起者签名 payload hash；
- v1 固定权限；
- 接受者 peer ID（使用后）。

### 关系记录

- 对方 peer ID 和最后验证的签名记录；
- 展示名称、网络和已审核端点；
- 关系凭证的受保护引用；
- `active`、`offline`、`revoked`、`needs_review`；
- 创建、最后联系和撤销时间；
- 权限版本；
- 不含内容正文的最后安全错误码。

### 发送记录

- message/content reference ID；
- 方向、接收 peer、创建时间；
- `queued`、`sent`、`delivered`、`failed`；
- 有界重试信息；
- 附件 blob 与元数据分离保存。

所有写入原子化，关系秘密不得进入 Webapp 响应。个人数据导出默认不包含可继续使用
的秘密。

## 7. 内容卡片协议

内容卡片只携带有界元数据和可验证引用：

```json
{
  "version": "ryn.shared-content-card.v1",
  "content_id": "...",
  "title": "...",
  "kind": "article",
  "source_url": "...",
  "publisher_peer_id": "...",
  "manifest_ref": "...",
  "size_bytes": 1234,
  "note": "可选的发送者短消息"
}
```

规则：

- 卡片必须由实际发送 Peer 签名或包含在已有加密签名消息中；
- `note`、标题和所有字段有明确大小上限；
- 接收方验证 Manifest、内容 hash、来源和安全策略；
- 卡片展示不等于信任发布者，也不提升信任等级；
- 自动下载默认关闭；
- 不支持的内容仍可打开原始来源或拒绝获取。

## 8. 产品页面

### 连接朋友

- 创建邀请；
- 扫描/粘贴；
- 可达性说明；
- 未使用邀请列表和取消。

### 连接 Review

- 验签状态；
- 简短指纹；
- 网络和端点分类；
- v1 权限的自然语言说明；
- 明确“不会获得什么”；
- 连接与取消。

### 好友列表

- 在线、离线、需确认、已撤销；
- 最后联系时间；
- 未读消息和未送达状态；
- 消息、分享、诊断和断开连接。

Peers 技术检查页可以保留在高级视图，但普通用户不应通过“Trust as root”来建立
好友关系。

## 9. 实施切片

### Slice 1：安全决策和本地关系 Store

- 批准 v1 可达边界和固定权限；
- 邀请、关系、撤销类型；
- 原子存储和秘密保护；
- 并发一次性消费测试。

### Slice 2：创建与接受

- 本地邀请 API；
- 本地 QR；
- Review 前零网络接触；
- 接受时轮换关系凭证。

### Slice 3：消息和小附件

- 现有 Peer Messenger 改用好友关系身份；
- 离线、未送达、重试和附件上限；
- 两节点首次发送验收。

### Slice 4：内容卡片

- 从我的内容选择并发送；
- 接收预览、验证和确认获取；
- 来源不可用和安全拒绝。

### Slice 5：撤销与恢复

- 本地立即拒绝；
- 远端通知；
- 保留/删除历史选择；
- 新邀请才能重新连接。

Private AI friends-only ACL 作为后续独立需求，在简单分享稳定之后实现。

## 10. 非目标

- 不做好友搜索、推荐、动态或群聊；
- 不做跨公网无条件连接承诺；
- 不开放 Private AI、VPN 或 Agent 权限；
- 不自动把好友变成 trusted root；
- 不做大文件无限传输和无限离线邮箱；
- 不引入账号系统或中心化联系人目录。

## 11. 验收标准

- [ ] 两台全新节点能通过 QR 或粘贴完成一次性配对。
- [ ] Review 在任何端点接触之前显示身份、网络、端点、有效期和权限。
- [ ] 邀请过期、取消、使用后和并发双重接受均安全失败。
- [ ] 配对不会修改 `trusted_roots`，也不会泄漏全局 network key。
- [ ] 配对后可发送一条加密消息和一个有大小上限的小附件。
- [ ] 可从“我的内容”发送内容卡片，接收方确认后才获取正文/文件。
- [ ] 离线、未送达和恢复状态对普通用户可理解。
- [ ] 撤销在本地立即生效，离线对方不阻塞撤销。
- [ ] 旧关系不能因重新发现 Peer 而自动复活。
- [ ] QR 生成不产生第三方网络请求。
- [ ] 日志、诊断、导出和验收材料不包含原始邀请或关系秘密。
- [ ] UI 不宣传超出已经物理验收的网络可达能力。

## 12. 两节点验收脚本

1. 节点 A 创建 15 分钟邀请；
2. 节点 B 扫描并检查 Review；
3. B 接受，双方看到好友状态；
4. A 给 B 发一条消息和一个小附件；
5. A 从“我的内容”发一张内容卡片；
6. B 查看卡片并主动获取内容；
7. B 离线，A 发送消息并看到未送达状态；
8. B 恢复后消息收敛；
9. A 断开连接，验证下一条请求被拒绝；
10. 重复过期、取消、双重接受和离线撤销负面测试。
