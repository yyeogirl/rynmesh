# 搜索中的损坏文档隔离与恢复

2026-09-12，开发分支候选。补充 SEARCH05、SEARCH07 和 G09；完整验收仍未通过。

## 问题与结果

真实存储回归先复现：一份文档的元数据损坏后，导入库列表返回“不可用”占位记录，搜索却继续读取不存在的 SHA256 字段，导致整次搜索返回 `search_source_unavailable`。正常阅读和聊天也无法检索。非法创建时间还会使文档列表排序失败。

现在逐份检查文档记录。损坏元数据不进入结果，合法元数据对应的正文不可读时只允许检索元数据；从不使用旧索引中的正文替代失败读取。创建时间损坏的条目显示为不可用，不影响其他条目的排序。文档控制文件不可用时跳过该文档范围，其他本地来源继续工作。离线下载已有的隔离分支也返回明确的范围提示。

查询增加 `unavailable_sources` 和 `indexing_pending`，前者只允许固定范围码，不包含异常、路径或文档标题。状态接口报告最近重建观察到的范围问题，查询和打开仍重新检查当前来源。磁盘索引格式不变，普通来源回调仍可返回列表。

页面区分“索引追赶中”和“部分来源不可用”。文档或下载不可用时提供 Settings / Offline reading 入口，保留正常结果，不显示误导性的完整“无匹配”。只有索引尚未更新时才自动重复查询；修复后可以刷新结果。不承诺搜索重建能够修复原始文件。

## 实际浏览器与 HTTP

Windows 单个独立 loopback 节点，端口 18920，后台工作器运行，无模型及公开发现。见 [HTTP 结果](source-isolation-http.json) 和 [浏览器步骤](source-isolation-browser.json)。

1. 初始实际 HTTP 查询得到三条合成结果；夹具只损坏其中一份文档的元数据。
2. HTTP 验证剩余两条、返回文档范围提示，损坏结果直接打开返回 409。
3. 浏览器输入关键词后显示两条正常结果和明确提示，没有“索引追赶中”的误导文案。正常保存文档可打开并读到正文，返回保留关键词。
4. 从提示进入 Settings → Privacy & data，正常副本和“Unavailable saved document”均可见，页面正常工作。
5. 测试夹具恢复原始元数据，后台索引更新后返回搜索，关键词保留、三条结果恢复、提示消失。恢复文件是合成夹具操作，不冒充用户界面的自动修复。
6. 关闭本轮浏览器和节点，端口已释放。

复现：在仓库环境先构建 webapp，使用 `scripts/accept_search_isolation.py --home <专用 rynmesh-search-isolation-acceptance 目录> --phase serve`；另一个终端依次执行 `damage`、`repair`、`verify`，期间按以上步骤操作浏览器。工具拒绝复用已有目录进行初始化。

本轮不证明打包桌面、跨网、所有来源存储故障、完整搜索缓存擦除或新的规模性能。G09 仍需覆盖其他功能组合及平台，原验收范围不缩减。
