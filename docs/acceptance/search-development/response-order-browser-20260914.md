# 搜索快速输入与迟到响应

2026-09-14，候选 `5c5b7e1`，Windows Chrome 和独立 loopback 节点。对应 SEARCH08。产品实现与前端资源未改动；仍为 `index-BcasDdVe.js`。

## 方法

专用新节点的真实会话存储包含 25 条合成归档消息：旧查询匹配 24 条，新查询匹配一条。无模型、无好友，不执行推理。

`scripts/accept_search_response_order.py` 在完整生产应用外包一层 ASGI 传输延迟器：先由原搜索接口计算响应，再暂缓发送。它不改搜索结果、状态码、查询实现或页面行为。控制文件释放旧响应；三次延迟均由明确释放结束，没有触发 180 秒保险超时。

已有组件测试覆盖忽略旧查询，但本次以实际页面和 HTTP 顺序补充证据，没有用组件测试代替联调。

## 页面检查

| 场景 | 操作与实际结果 |
|---|---|
| 旧首屏慢、新首屏快 | 确认旧响应被挂起后改关键词，新结果先显示一条；释放旧响应后仍是新关键词、一条新结果、零条旧结果 |
| 旧下一页慢、新首屏快 | 先显示 20 条并点击 Load more results；确认第二页挂起后改关键词。新结果先显示一条，旧第二页释放后没有混入旧记录 |
| 下一页等待时清空 | 再次从 20 条结果请求第二页，点击 Clear filters and keywords。释放第二页后关键词仍空，结果仍空，恢复输入说明；没有自动重新填回 |
| 连续快速修改 | 一次连续操作中三次修改输入值（总工具执行约 156 ms），最终仅发起一条最终关键词请求。页面显示一条正确结果，没有旧结果 |

浏览器最终 warning/error 记录为空。表中计数和页面状态在实际操作后读取，没有向页面注入响应或修改 React 状态。

## HTTP 顺序与限制

[HTTP 记录](response-order-http-20260914.json)共八次查询。旧首屏延迟 **33.359 秒**，旧第二页延迟 **36.547 秒**，清空时的第二页延迟 **29.922 秒**。前两个场景均明确记录新响应发送完成早于旧响应释放，所有响应状态为 200。

首屏请求有 AbortController，服务端记录的发送不等于浏览器仍使用该请求；分页路径没有同样的请求取消参数，实际页面仍通过请求代次丢弃旧结果。此区别保留，不把服务端发送冒充为旧内容曾被页面渲染。

只保存请求编号、查询摘要、是否分页、状态及时间，不记录查询原文或正文。观察器 `verify` 核对响应顺序、延迟和请求数；Ruff 通过。无产品代码修改，未重跑性能或整库测试。

复现需仓库虚拟环境与 `PYTHONPATH` 指向当前仓库。先运行脚本 `serve`（拒绝复用已有目录），按表进行页面操作；在相应请求前切换 `hold-first` / `hold-page`，确认 `events` 出现 held 后操作新查询或清空，再以 `none` 释放。最后 `verify` 保存本次确定序列的证据。

本轮没有覆盖延迟错误响应、所有键盘路径或打包桌面。原始 SEARCH08 和通用平台门槛仍保持候选状态。页面与节点在记录结束后关闭。
