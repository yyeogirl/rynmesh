# 已保存文档的审核清理与恢复

2026-09-11，开发分支候选，补充 G08 的文档文件范围。完整八项需求验收仍未通过。

## 修复与范围

原流程递增下载代数后直接递归删除目录。Windows 文件占用可能导致部分文件已删、部分仍在，重启后没有原任务可继续；再次“全部清理”还可能选中后来新保存的文档。

现流程先审核指定文档或当前全部文档的文件数量、字节数及完整性，确认后将下载屏障和持久清理凭据一起原子提交。所选文档立即停止新的读取/分享，剩余文件按审核记录删除。删除失败保留原任务，页面显示未完成；重启后可继续。文件发生变化需要重新审核，未知文件名、子目录、链接及可识别的未来格式均保留，不递归扩大删除范围。

范围包含受管理的原文件、提取正文、元数据、修复备份及中断写入文件。消息、卡片、阅读收藏、独立离线下载、搜索缓存、浏览器和其他人的副本分别处理，不宣称全部擦除。开始前已读取到内存或已发送的字节无法召回。

待处理的同一文档 ID 暂时不能重新保存或修复，界面说明先继续清理；不同文档仍可保存。清理完成后可主动重新获取同一文档，重复旧任务不会误删它。旧下载响应携带的代数失效，不自动恢复已清理文件。更早任务在后来清理开始后不再接受，必须重新审核。

## 存储与接口

`library-imports/control.json` 从整数版本 1 升为 2，内嵌 `ryn.library-cleanup.v1`。v1 只读不会迁移，首次清理前保留原始 `control.json.v1.migrated`；失败不覆盖来源。未知控制扩展保留，未来版本拒绝。控制记录只含生成的文档 ID、固定文件名、数量、SHA256 和任务状态，没有正文或原始用户文件名。已完成任务移除文件清单，只保留当前结果、范围和单调代数。

每次最多 2000 个目录、16000 个受管理文件，控制文件仍受 4 MiB 序列化上限限制。实际清单超限会在来源提交前失败，可缩小选择范围；没有为通过检查而丢弃记录。读取、导出和保存复用同一 `.imports.lock`，不新增后台线程或网络任务。

Owner 接口位于 `/api/local/privacy/documents`，支持审核、任务查询/提交/继续、剩余文件审核/确认。请求体上限 8192 字节，安装可重复、每次取当前 Owner 和存储。旧 DELETE/clear 接口现在也要求审核令牌；无令牌返回 409。设置页和分享卡片已改用审核流程；分享卡片列表依当前文档状态显示不可用，不写回过时标记覆盖后来重新下载的状态。

## Windows 实际验收

见 [HTTP 复核](document-cleanup-http.json) 和 [浏览器记录](document-cleanup-browser.json)。单个独立 loopback 节点，端口 18920，专用合成目录，无模型、无公开发现。

1. 原始合成文档可以通过实际 HTTP 阅读。Windows 句柄保留读写共享、拒绝删除共享。
2. 设置页审核显示一份文档、三个文件、0.8 KiB。键盘取消后再次审核，数量未变化；键盘确认后复现文件删除失败，错误获得焦点、任务显示未完成。
3. HTTP 确认待清理文档不可读（409），同 ID 保存被拒绝；通过合成夹具直接保存另一份文档，验证不受该任务影响。此保存不是用户页面操作。
4. 终止节点并用同一目录重启，页面保留原任务，显示后来保存的 `later.txt`。合成夹具改写剩余被占用文件，点击继续被拒绝并提示重新审核。
5. 页面重新审核剩余一个文件，释放句柄后键盘确认完成。结果获得焦点，`later.txt` 仍在。
6. 实际 HTTP 复核原任务完成、新文档仍可读；夹具重新保存原内容得到相同 ID，再重放旧完成请求，正文哈希仍与初始一致，阅读收藏保留。

工具为 `accept_friend_feed_node.py`、`hold_acceptance_download.py --document-id` 和 `accept_document_cleanup.py --phase prepare|pending|verify`；只操作专用合成验收目录。节点、句柄和浏览器已关闭，端口释放。

尚未用打包桌面或跨网环境验收；分享卡片清理有自动交互和完整节点路由证据，本轮没有双人浏览器实测。搜索派生副本协调、其他个人数据范围和通用验收仍需继续。
