## 范围与恢复

Settings → Privacy & data → Friend update data 可审核发布/草稿、正在发布条数、关注、收到的更新和已知备份数量，再确认清理。提交会停止审核的发布、清除草稿和收件列表、关闭现有关注。好友关系、私信、分享卡片、已保存文档、阅读收藏和离线下载保留；其他人或浏览器保存的副本无法召回。

来源变更与持久清理凭据同一次原子提交。备份删除失败时页面区分已完成来源和未完成备份，重启后可继续原任务；变化备份需要重新审核。来源提交前可关闭确认弹窗，提交后不提供撤销成功的承诺。新发布、主动重新关注不会被旧清理请求重试误删。

新增 `ryn.friend-feed.v2` 及内嵌 `ryn.friend-feed-cleanup.v1`。新存储使用 v2，旧 v1 普通读写保留原版本，仅明确清理时先保存原始加密 `.v1.migrated` 再升级。保留未知顶层扩展，拒绝未来版本。发布删除标记最多 10000 条，达到容量明确拒绝新清理，不淘汰旧标记；仍遵守 12 MiB 明文、17 MiB 文件上限。

旧草稿请求不能重建已删除发布 ID；关注修订阻止旧启用请求和迟到刷新恢复内容；正文发送前再次核对权限。只保留当前/最近任务及单调序号，后来任务开始后更早请求须重新审核。备份按精确文件名、字节数和 SHA256 删除。

实际浏览器首次尝试发现后台轮询更新检查时间和加密字节，导致内容未变时审核失效。已修复为忽略纯轮询记账字段，仍绑定发布、受众、关注修订、内容和已读状态。v1 待生成备份在提交锁内核对内容后记录实际字节；独立备份变化仍使审核失效。v1/v2 回归覆盖轮询不使审核失效、已读变化使审核失效。

## 三节点实际操作

Windows 独立进程、目录和身份 Author/Bob/Carol，端口 18920–18922，无模型、无公开发现。见 [HTTP 复核](cleanup-http.json) 与 [浏览器记录](cleanup-browser.json)。

1. 真实邀请配对后 Bob/Carol 主动关注。Author 仅向 Bob 发布合成正文；Bob 一条、Carol 零条。Bob 保存独立副本并标记已读。
2. Bob 从设置页审核、键盘确认清理，来源和备份两步骤完成，已保存文档仍为一份。
3. Windows 文件句柄占用 Author 的合成中断写入备份。页面审核一条发布和一个备份；先取消弹窗再确认。删除失败时来源已清、备份待处理，错误获得焦点；此时 HTTP 验证旧发布获取已被拒绝。
4. 终止并用原目录重启 Author，页面仍显示同一任务及剩余备份。释放句柄后点击继续，两步骤完成，结果获得焦点。
5. HTTP 验证双方来源清理、旧发布获取 409、独立正文哈希不变、好友关系保留。创建新发布并主动重新关注，重复双方已完成的旧清理请求，新内容仍存在；Bob 实际页面显示新发布为未读。

复现工具：`scripts/accept_friend_feed_node.py`、`scripts/accept_friend_feed_cleanup.py --phase prepare|verify`、`scripts/hold_acceptance_download.py --feed-orphan <32hex>`，只允许专用合成目录。准备及最终复核为真实 HTTP；清理确认、取消、继续为实际浏览器操作。

这是同机 loopback 证据，不是打包桌面、跨 NAT 或远端擦除验收。变化备份重新审核及 v1 迁移只有本轮自动测试证据。完整账户清理、其他数据范围及通用标准仍待完成。
