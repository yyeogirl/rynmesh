# Ask 好友连接失败与重启恢复验收（2026-09-14）

范围：Windows、本机两个独立身份/数据目录、真实原生 CPU 模型、正常浏览器 Ask 入口。复用已通过页面配对并授权的测试节点。网络只有本机 host 路径；未进行不同公网出口、GPU 或打包桌面验收。

## 已实际完成的流程

| 场景 | 实际结果 |
|---|---|
| 消费端强制 ICE，固定 UDP 18961 被真实已收集候选的 ICE 会话占用，再由浏览器发单 | 返回 p2p_capacity_exhausted；页面提示连接会话不足、等待活跃会话关闭。Provider 没有收到这笔推理 |
| 关闭占用会话，再创建、关闭另一 ICE 会话验证同端口可重新绑定 | 两次均取得两个 host 候选；实际 UDP 端口由本轮消费节点持有。占用会话未建立对端连接，不声称它已完成数据传输 |
| 点击原失败任务的 Check original task | 保留原失败，不重新发单、不重复释放额度 |
| 释放端口后在页面审核并发送新请求 | 真实模型正确回答，传输证据为 ice_udp_direct / host_direct / relay_used=false；一次结算、一次 Provider 收入 |
| 恢复默认自动连接，停止好友节点，页面尝试发送 | 明确原 Provider 不可用，草稿保留；没有新增任务或订单 |
| 审核后停止好友并确认发送 | 成功复现实际直连失败；发现默认自动模式丢失具体连接原因，只显示普通失败 |
| 修复后重做人工断开 | 此次断开发生在提交前，只验证了草稿保护，不能作为修复后传输失败证据 |
| 浏览器提交真实长请求，辅助进程观察到 Provider 新任务为 running 后才停止该 Provider | 实际断开正在进行的请求；修复后的页面显示直连失败，提示检查连接、核对原任务 |
| 重启 Provider | 发现原任务仍标 running；补充启动恢复后，原任务明确 failed / provider_restarted_before_completion，不伪造成功或声称模型运算立即停止 |
| 页面检查原中断任务，再审核发送另一新请求 | 检查不发新单；新请求经 peer_http_direct 成功，真实模型正确回答，结算和收入各一次 |
| 最后两端都重启，再检查原容量失败和原直连失败 | 会话、任务、授权、余额及额度事件不变；页面仍确认原任务失败且未重新提交 |

本轮新会话：`cb4d3f76-2436-4cc0-8905-9207cd654a51`。共五笔新增任务：容量不足、ICE 成功、修复前普通直连失败、修复后运行中断、恢复后直连成功。三个失败各 hold/release 一次、没有 Provider 收入；两个成功各 hold/settle 一次，Provider 各记一次 0.001 DEV_TASK_BALANCE 收入。这是开发测试额度。

所有原有会话摘要保持不变。最终双节点重启前后，两端会话、订单、授权、余额和事件逐项相同。修复前普通错误及 Provider 悬挂状态都保留在早期检查点中，不改写历史证据。

## 修复

1. 分开记录连接策略与实际尝试的传输方式。自动策略的直连失败现在保留 direct_transport_failed；配置中转时继续尝试中转，中转失败保留 encrypted_relay_failed。未改变连接选择或自动重试规则。
2. 节点启动、接收请求前将遗留 created/accepted/running Provider 任务置为明确失败。终态任务保持原样，重复启动不追加恢复事件。原签名请求重复到达时，返回原重启失败原因而不重新推理、不等待一个已经不存在的工作线程。
