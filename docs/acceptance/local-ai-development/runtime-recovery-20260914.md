日期：2026-09-14，Asia/Hong_Kong。候选基线 `ce2f964`，加本次状态提示修复；最终生产前端 `index-DPwKlihB.js`。环境为 Windows AMD64、独立本机节点、生产前端与真实 llama.cpp CPU runtime；不是打包桌面应用。没有手工写入模型配置或会话，也没有替换下载响应、推理结果或进度。

## 安装失败恢复

1. 重开 Services → Manage，确认页面保留 managed、light、local-small 和端口，显示来源、许可、资源需求及校验失败说明。下载确认未勾选时重试禁用。
2. 勾选并点击 Retry configuration。沿正常安装路径重新获取运行时；已完成的真实模型重新校验后复用，没有复制旁路文件。
3. 页面依次显示准备运行时、100% succeeded、本机就绪。实际加载与推理自检完成，发布开关始终关闭。14:42:06 仍在下载运行时，14:43:18 已确认成功；这不是整个 469 MiB 模型的下载耗时。

固定的六个平台文件大小、SHA-256 均与 [llama.cpp b10774 官方发布](https://github.com/ggml-org/llama.cpp/releases/tag/b10774) 一致，见 [固定资产审计](runtime-pin-audit-20260914.json)。独立下载 Windows 资产得到 18380733 字节，摘要吻合，耗时 18.984 秒，见 [下载审计](runtime-download-audit-20260914.json)。该独立下载只用于核对，正常安装没有使用它。旧失败文件已被原安装器丢弃，不能据此断言旧故障具体由何种网络或文件损坏造成；没有修改固定摘要或跳过校验。

## 本轮修复与检查

实际发现 Services 将停止的本机模型标成 offline / Provider offline。统一 Services、Ask 首页和聊天页的服务状态提示：本机未就绪提供模型管理入口；容量用尽显示忙碌；远端缺少可用性证据显示需要刷新，不断言节点离线。本机就绪也不再称为远端发现结果。配置和权限逻辑保持原行为。
